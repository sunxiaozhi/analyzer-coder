# 系统实战能力评估

日期：2026-09-05；代码基线：ae851bb，当前工作区。

## 结论

系统具有工程上下文与变更治理平台的实际代码基础，适合修复交付阻断后开展单仓库、有人复核的内部试点。目前不足以作为无人值守的正式合并门禁，也没有足够证据证明已达到多团队生产平台的可靠性要求。

主要差距：交付流水线断点、门禁回报可信性、不完整审查的状态语义、崩溃恢复、机器身份、真实质量验收及旧库升级。继续增加页面不是当前最高优先级。

本次抽查核心代码、运行现有测试与前端构建，没有修改业务代码、操作真实 PR 或生产数据库。原有 demo-projects/smart-retail-platform 子模块改动未动。

## 产品价值和痛点

建议定位：面向研发团队与 Coding Agent 的版本化工程上下文和变更审查平台，让每次修改能查到适用规则、必测项、审批要求与可追溯证据。

| 用户痛点 | 当前机制 | 生效边界 |
| --- | --- | --- |
| 老项目靠熟人解释，新人定位慢 | 仓库索引、检索、问答、代码证据工作台 | 检索命中与引用覆盖不等于结论正确 |
| Agent 每次都要重复解释项目规则 | 版本化任务上下文、MCP、工程知识 | 团队必须维护并审核规则 |
| 改完不知道还要测什么、找谁确认 | Git Diff、符号映射、Scope、测试审批义务 | 未维护的隐性业务规则不会自动变成可靠门禁 |
| 文档与代码不一致 | 代码引用、内容哈希、知识漂移与复核 | 知识需绑定范围和负责人 |
| AI 回答难核实 | 事实、审核知识、图谱推断、建议、未知分开 | 当前明确不等同于语义证明 |
| 人、Agent、PR、CI 各用一套规则 | 共用审查、证据与结果反馈接口 | 机器身份和可信回报仍需补齐 |

最有价值的资产是经过维护的工程知识及代码适用范围。代码搜索、问答、图谱是入口；减少组织约束遗漏并发现知识过期，应是产品主要收益。

## 架构与已有基础

Vue 3/TypeScript 前端 → Java 17/Spring Boot/MyBatis 后端 → PostgreSQL/pgvector；Git 与 CodeGraph CLI 处理仓库/图谱；Node stdio MCP 调用后端 API。后台任务主要由数据库任务表和 Spring Scheduler 执行。

业务主线：仓库接入 → Git 版本/受管快照 → 索引和 Diff → 匹配已审核知识 → 测试、审批、证据、未知项 → Web/MCP/PR/CI → 知识漂移和复核。

应保留：当前快照隔离、不可变审查结果、请求幂等、知识审核/发布状态分离、模型不直接决定 CI、凭据加密、仓库权限、事实和推断分开。项目有实际实现和测试，并非只有展示页面。

## 主要问题、优先级和验收建议

### 1. P0：Linux CI 有明确断点

证据：.github/workflows/linux-ci.yml:61 调用 scripts/start.ps1，但文件不存在。evaluation/change.jsonl:1 的 CHG-001 引用已删除的 V3__qa_citation_assessment.sql。实际执行 evaluate-quality.mjs --validate 失败，相关回归测试也失败。

这些步骤在后端、数据库和前端测试之前，写有测试步骤不意味着当前 CI 能执行到它们。

建议：修正启动契约；逐项复核迁移合并后的金标准路径及预期含义；从干净 Linux checkout 跑全链路。不能仅删除失败样本或机械替换路径。

验收：PR/default branch 全绿，发布标签使用当前版本的真实质量报告。

### 2. P0（正式门禁前）：测试/审批回报不是可信证明

证据：interfaces/rest/CiCheckController.java:35 只要求仓库 READ；application/ci/CiCheckService.java:53 从请求建立测试和审批索引，第 127、168 行按上报状态检查义务；evidenceUrl 没有在该决策链中用于向提供方核验。

影响：它当前适合作为“依据给定回报计算决策”的评估器。具备 READ 的调用方可以填 PASSED 和某审批账号 APPROVED；PASS 本身不证明测试真实运行或该人员批准。该接口不会直接合并 PR，但若将它的输出作为正式门禁，就存在信任缺口。

建议：保留试算；正式检查从受信 CI 和代码托管平台读取结果，绑定 repository、精确 Head SHA、workflow/run ID、审批身份和时间。未验证回报保留 REPORTER_ASSERTED，不满足 VERIFIED 级强制义务；测试义务使用稳定 ID。

GitHub Check Run 可绑定具体 Commit SHA，可作为集成基础；审批需另行读取并核验提供方记录。[GitHub 官方说明](https://docs.github.com/en/apps/creating-github-apps/writing-code-for-a-github-app/building-ci-checks-with-a-github-app)

### 3. P0（正式门禁前）：不完整审查也可能 PASS

证据：CiCheckService.java:63 仅以 blockers 是否为空产生 PASS/FAIL；第 283、295 行把 partial change 和 unknowns 设为非阻断提示。CiCheckServiceTest.java:260 附近明确断言该类组合可以 PASS。

影响：“没发现确定违规”和“检查充分、允许放行”被混在一起。遗漏 Diff 可能使本应触发的规则完全没有进入 blocker。

建议：增加 INCONCLUSIVE/NOT_READY，按未知原因分级。可选模型或非必要图谱不可用只提示；Diff 不完整、关键版本不一致、强制规则无法评估应阻止自动放行，转人工处理。不要把所有未知都说成代码违规。

验收：截断 Diff、关键上下文缺失不返回可放行成功；仅模型不可用仍能完成确定性检查。

### 4. P1：普通索引与任务审查崩溃恢复不足

证据：mappers/IndexJobMapper.xml:64 的 FULL/INCREMENTAL 领取只写 RUNNING/started_at，与第 70 行写 timeout_at 的按类型领取不同。worker/IndexJobWorker.java 仅轮询执行。TaskReviewService.java:109–117 先写 RUNNING，同请求重试返回已有记录；TaskReviewMapper.xml 未发现审查租约/过期回收操作。

静态推断：写入 RUNNING 后进程退出，任务可能残留；同幂等请求不会自动继续。CodeGraph/知识漂移已有部分超时机制，不能泛化为所有任务都可恢复。本次未做故障注入。

建议：统一租约、心跳、过期回收、重试上限；审查成为可恢复作业，或重启时明确标记中断失败；最终发布仍需版本条件和唯一约束。

验收：索引、图谱、审查运行中终止进程再重启，最终可解释、可重试且不重复发布。

### 5. P1：MCP/CI 依赖人类登录会话

证据：mcp-server/README.md:7–16 需要网页登录 Session/CSRF；scripts/ci-task-review.mjs 同样使用 Cookie。application.yml:57–59 默认空闲 30 分钟、绝对 12 小时失效。

影响：适合临时交互，长期 Agent/定时 CI 可能需要人工续凭据。

建议：服务账号、仓库范围、上下文读取/审查创建/结果上报独立权限、短期凭据及撤销轮换；审计区分人和机器。不要单纯延长人类会话。

### 6. P1：任务审查的图谱符号查询未发现生产接线

证据：ChangedSymbolResolver.java:47 注入 List<CodeGraphSymbolLookup>，第 168 行列表为空即跳过。当前 src/main 对接口的引用仅在该类内，未发现实现 Bean；随后使用源码声明规则、Chunk 或文件降级。CodeSymbolExtractor.java:15–25 明确使用轻量规则及正则。独立 CodeGraphService/ManagedCodeGraphService 和传播接口确实存在。

影响：不能从“系统有图谱”推导“任务审查已完整覆盖真实调用关系”。直接文件/路径匹配有价值，复杂声明、动态分派、跨文件影响仍需验证。

建议：接入真实图谱符号适配器并对齐 snapshot/commit；按主要用户语言补解析器和真实样本；公开语言、关系和降级覆盖范围。先验证 Java/Vue，再扩语言。

### 7. P1：缺少可放行的真实质量证据

证据：manifest 有 50 定位、30 问答、20 影响、10 审查、8 漂移样本；evaluation/README.md:16 说明新增标签待具名人工复核。当前未发现完整发布结果，结构校验也因旧路径失败。

“三类形态”是本仓库 Java/Vue/运维文件，不能等同三个独立业务仓库。现有数据库 IT 确实存在；RepositoryImportToAskIT 使用 mock LLM 和本地证据降级，不能证明外部模型质量，也不是真实浏览器业务端到端验收。

建议：在实际业务仓库建人工金标准，再增加独立仓库；旁路审查真实 PR，统计误报/漏报、关键规则召回、必测项遗漏、证据完整率、延迟和成本。已有 thresholds.json 可复用，补运行可靠性和关键规则覆盖指标。

### 8. P1：旧数据库没有直接原地升级路径

证据：迁移目录仅 V1__init_schema.sql；docs/08-linux-git-deployment.md:437 明确不兼容旧 V1–V14 历史，需要备份、导出、重建、回灌。这是已经承认的限制，不代表每个新安装都会失败。

建议：分别定义新装与旧库升级；提供受支持的增量迁移或演练后的转换流程，核对账号、权限、知识修订、证据和凭据保留；后续已发布迁移保持不变。Flyway 会记录校验和以检测已应用迁移变化。[Flyway 官方说明](https://documentation.red-gate.com/fd/versioned-migrations-273973333.html)

### 9. P2：规模和运维仍需实测

默认快照上限 20,000 文件/2 GiB、索引单文件 512 KiB 是资源边界，不应直接视为缺陷。前端主 JS 约 1.64 MB、gzip 533 KB，有包体警告，建议路由拆分后测首屏。当前没有本次实测的并发吞吐、长时间稳定性、备份恢复、磁盘增长或模型成本，不能承诺企业级容量。

建议：以目标仓库规模测冷/增量索引、排队和审查 P95；观测队列年龄、失败重试、产物新鲜度、存储和外部调用成本；实际演练备份恢复。

## 落地顺序与收益验证

1. 恢复交付：修 CI、复核金标准、独立测试库和干净 Linux 安装；明确旧库升级范围。
2. 聚焦一个业务仓库：挑 10–20 条高价值规则，来自历史缺陷/架构决策/接口约束，绑定负责人、文件或符号、必测项和审批。
3. 先旁路审查约 20–30 个真实改动，人工核对遗漏与误报；测找规则时间、Agent 上下文补充时间、审查耗时和必测项遗漏。这些是建议规模，不是已有结果。
4. 补可信机器链路：服务身份、精确版本、真实测试/审批回报、INCONCLUSIVE、故障恢复。
5. 逐条开启强制规则，并提供具名、有期限、可审计的例外流程。
6. 最后扩跨仓库和高级推理。当前单仓库真实验收未完成而跨仓功能已开发，建议暂缓扩面。

试点例子：修改退款接口 → 命中业务确认过的退款规则 → 指出幂等与权限测试 → 找到支付负责人 → 核对本次 Commit 的真实测试/审批 → 提醒规则文档复核。模型不能自行把猜测升级成强制政策。

进入正式使用的判断依据应是：真实仓库可重复运行、关键失败不伪装成成功、门禁证据可信、重启可恢复、升级/备份可演练，以及确实减少团队时间或遗漏。页面数量与单元测试数量不能替代这些验证。
