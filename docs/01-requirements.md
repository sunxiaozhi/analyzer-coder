# 代码智库系统需求文档

版本：v0.2  
日期：2026-07-19  
状态：已完成首轮需求评审，关键产品决策待确认

## 1. 背景

团队希望基于 CodeGraph 构建一个代码智库系统，将代码结构解析后的 SQLite 数据与 RAG 能力结合，为代码理解、代码检索、调用链分析、影响范围分析、研发问答和知识沉淀提供统一入口。

传统 RAG 对代码的理解主要依赖文本相似度，容易遗漏调用关系、定义位置、符号依赖和跨文件影响。CodeGraph 可以补充结构化代码事实，包括符号、文件、调用边、引用关系和影响面。系统目标是把“语义检索”和“结构化代码图谱查询”结合起来，输出带代码引用、可追溯、可验证的回答。

## 2. 产品目标

### 2.1 核心目标

1. 支持导入一个或多个代码仓库，自动构建代码知识索引。
2. 同时利用 RAG 向量检索和 CodeGraph SQLite 结构化数据进行混合检索。
3. 支持自然语言代码问答，并返回代码文件、符号和行号引用。
4. 支持函数、类、文件级别的调用链和影响范围分析。
5. 支持增量索引，使仓库变更后知识库可以更新。

### 2.2 非目标

v0.1 不优先覆盖以下能力：

1. 自动修改代码并提交 PR。
2. 完整替代 IDE。
3. 大规模企业级权限矩阵和审计系统。
4. 跨组织公网 SaaS 多租户计费。
5. 训练私有代码大模型。

## 3. 目标用户

1. 研发工程师：快速理解陌生模块、查找实现位置、定位调用链。
2. 架构师 / Tech Lead：评估模块依赖、改动影响面、架构边界。
3. 新成员：通过问答快速理解代码库和业务逻辑。
4. 代码审查人员：辅助判断改动是否影响其他模块。
5. 运维 / SRE：定位运行链路中对应的代码实现。

## 4. 典型场景

### 4.1 功能定位

用户问题：

> 登录鉴权逻辑在哪里实现？

系统应返回：

1. 相关文件和符号。
2. 核心函数或类说明。
3. 代码引用位置。
4. 相关入口和调用方。

### 4.2 调用链分析

用户问题：

> validateToken 被哪些地方调用？

系统应返回：

1. 直接调用方。
2. 多层调用链。
3. 文件路径、符号名、行号。
4. 可视化调用图数据。

### 4.3 改动影响分析

用户问题：

> 如果修改 OrderService.createOrder，会影响哪些模块？

系统应返回：

1. 直接和间接受影响的调用方。
2. 相关测试文件。
3. 高风险依赖。
4. 建议验证范围。

### 4.4 业务知识问答

用户问题：

> 订单取消后库存是如何回滚的？

系统应返回：

1. 语义相关代码片段。
2. 关键业务流程总结。
3. 涉及的服务、函数、事件或数据库操作。
4. 引用来源。

### 4.5 代码资产沉淀

用户希望系统沉淀：

1. 模块说明。
2. 架构说明。
3. API 说明。
4. 常见问题。
5. 代码变更知识。

## 5. 功能需求

### 5.1 仓库管理

优先级：P0

系统应支持：

1. 通过本地 Git 路径、远程 Git 地址、GitLab 项目和 ZIP 上传四种来源创建代码仓库。
2. 记录仓库名称、来源类型、受管代码目录、默认分支、当前 commit 或上传版本。
3. 对远程 Git 和 GitLab 仓库执行手动同步，拉取指定分支的最新版本。
4. 对 ZIP 仓库重新上传压缩包，并以原子方式覆盖当前代码版本。
5. 查看代码版本、同步状态、CodeGraph 状态和知识索引状态。
6. 触发全量索引；具备可靠变更检测后再开放增量索引。
7. 删除仓库的平台记录、受管代码副本和索引数据。

验收标准：

1. 用户可以分别通过本地 Git、远程 Git、GitLab 和 ZIP 创建仓库。
2. 系统能区分来源类型，并显示 commit 或 ZIP 上传版本。
3. 远程 Git/GitLab 同步失败时保留同步前代码版本；ZIP 覆盖失败时保留原代码目录。
4. ZIP 重新上传成功后仓库 ID 不变，代码版本更新，旧索引标记为“可能过期”并触发全量索引。
5. 系统可以显示同步进度、索引进度、最后同步时间和最后索引时间。
6. 同步或索引失败时可以看到面向用户的错误摘要。

### 5.2 CodeGraph 集成

优先级：P0

系统应支持：

1. 检测仓库是否存在可用的 `.codegraph/` 目录，并校验版本、数据文件和最小 schema。
2. 由平台调用受支持版本的 CodeGraph CLI，对当前代码快照执行首次分析和重新分析。
3. 将 CodeGraph 分析作为后台任务执行，记录任务状态、阶段、进度、耗时、日志和错误摘要。
4. 读取 CodeGraph 生成的 SQLite 数据，通过适配层查询文件、符号、定义、引用和调用关系。
5. 不直接让业务逻辑依赖 CodeGraph 原始表结构；schema 变化的影响限制在适配层。
6. 将 CodeGraph 产物绑定仓库代码版本：Git 使用 branch/commit，ZIP 使用上传版本和内容摘要。
7. Git 同步或 ZIP 覆盖成功后检测代码版本变化，并将现有 CodeGraph 标记为“已过期”。
8. 支持从仓库管理页触发分析，并在索引任务页统一观察 CodeGraph 分析和知识索引任务。
9. 支持“CodeGraph 分析成功后自动创建知识索引任务”的可选串行流程。

验收标准：

1. 新仓库没有 CodeGraph 时可以触发首次分析，任务完成后状态变为“可用”。
2. 可以通过符号名查询定义、caller、callee、文件符号和代码位置元数据。
3. 分析产物记录其对应的代码版本，代码更新后能够准确显示“已过期”。
4. 重新分析失败时保留上一版可用 CodeGraph，不影响仍绑定旧代码版本的查询。
5. 任务页面可以查看阶段、进度、日志摘要、失败原因并重新执行。
6. 未安装 CLI、版本不兼容、超时和资源不足具有不同错误码和用户提示。

### 5.3 RAG 索引

优先级：P0

系统应支持：

1. 按代码结构切分 chunk，优先粒度为函数、类、方法、模块说明。
2. 对 README、Markdown、API 文档等文档内容进行段落级切分。
3. 为每个 chunk 生成 embedding。
4. chunk 元数据应包含仓库、commit、文件路径、符号 ID、符号名、起止行、语言、chunk 类型。
5. 支持删除和重建索引。

验收标准：

1. 对一个仓库索引完成后，可以查询 chunk 总数。
2. 任意 chunk 都可以追溯到文件路径和行号。
3. RAG 检索结果可以返回相关代码片段。

### 5.4 混合检索

优先级：P0

系统应支持：

1. 向量语义检索。
2. 关键词 / 符号名检索。
3. CodeGraph 结构化查询。
4. 基于调用关系扩展上下文。
5. 对多路召回结果进行合并、去重、排序。
6. 根据问题类型选择检索策略。

问题类型至少包括：

1. 功能定位。
2. 符号解释。
3. 调用链查询。
4. 影响分析。
5. 测试建议。
6. 架构说明。

验收标准：

1. 对“某功能在哪里实现”类问题，返回语义相关代码。
2. 对“某函数被谁调用”类问题，返回 CodeGraph 调用关系。
3. 对混合问题，结果同时包含代码片段和结构化关系。

### 5.5 代码问答

优先级：P0

系统应支持：

1. 用户输入自然语言问题。
2. 系统检索相关上下文。
3. LLM 生成答案。
4. 答案必须包含引用来源。
5. 当检索证据不足时，明确提示不确定。

验收标准：

1. 回答中至少包含文件路径或符号引用。
2. 不应编造不存在的文件、函数或业务逻辑。
3. 对低置信度问题给出限制说明。

### 5.6 调用图和影响分析

优先级：P1

系统应支持：

1. 输入函数、类、文件或符号。
2. 查询直接 caller 和 callee。
3. 查询多层调用链。
4. 返回图结构数据，供前端可视化。
5. 给出影响范围摘要。

验收标准：

1. 可以查看某个函数的上下游依赖。
2. 可以限制调用深度。
3. 可以按文件、模块、符号聚合影响范围。

### 5.7 知识沉淀

优先级：P2

系统可支持：

1. 自动生成模块说明。
2. 保存人工确认后的知识卡片。
3. 将问答结果沉淀为 FAQ。
4. 将知识卡片纳入后续 RAG 检索。

验收标准：

1. 用户可以保存一条知识卡片。
2. 后续提问可以检索到该知识卡片。

### 5.8 前端界面

优先级：P1

系统应包含：

1. 仓库列表。
2. 索引状态页面。
3. 问答页面。
4. 检索结果引用区。
5. 代码片段查看器。
6. 调用图查看器。

验收标准：

1. 用户可以完成从导入仓库到提问的闭环。
2. 用户可以点击引用查看代码片段。
3. 用户可以查看调用关系图。

## 6. 非功能需求

### 6.1 准确性

1. 所有答案必须基于检索证据。
2. 结构化代码关系优先使用 CodeGraph 数据。
3. RAG 结果必须带来源。

### 6.2 性能

MVP 目标：

1. 单仓库 10 万行代码内，全量索引可在可接受时间内完成。
2. 普通问答响应时间目标小于 10 秒。
3. 纯结构化调用链查询目标小于 2 秒。

### 6.3 可扩展性

1. 支持多仓库。
2. 支持替换 embedding 模型。
3. 支持替换向量数据库。
4. 支持扩展检索策略。

### 6.4 安全性

1. 代码仓库路径和索引数据应本地或私有化保存。
2. 调用外部 LLM 时应明确哪些代码片段会被发送。
3. 支持关闭外部模型，切换为本地模型。
4. 后续企业版应支持用户权限、仓库权限和审计日志。

### 6.5 可观测性

1. 记录索引任务日志。
2. 记录检索命中的 chunk 和符号。
3. 记录 LLM 调用耗时和 token 使用。
4. 支持查看失败原因。

## 7. 数据范围

### 7.1 纳入索引

1. 源代码文件。
2. README 和 Markdown 文档。
3. API 文档。
4. 测试文件。
5. 配置文件中的关键内容。

### 7.2 默认排除

1. `.git/`
2. `node_modules/`
3. `dist/`
4. `build/`
5. 二进制文件。
6. 大型生成文件。
7. 密钥、证书、环境变量文件。

## 8. MVP 范围

为避免首期同时交付过多高风险能力，MVP 拆分为三个可独立验收的里程碑。

### 8.1 M0：仓库和索引闭环（当前优先）

1. 添加、查看、同步和删除本地 Git、远程 Git、GitLab、ZIP 仓库记录。
2. 校验代码来源并记录 commit 或 ZIP 上传版本。
3. 检测已有 `.codegraph/`，并能通过平台触发首次分析和重新分析。
4. 在统一任务中心展示 CodeGraph 分析与知识索引的阶段、进度、耗时和失败原因。
5. CodeGraph 分析成功后触发全量知识索引，并以版本化产物保护上一版结果。
6. 浏览和关键词查询已生成的 chunk，并能定位文件和行号。
7. 完成仓库管理、添加仓库、CodeGraph 操作和任务详情前端页面。

M0 不要求 embedding、LLM 问答或调用图可视化。

### 8.2 M1：检索和问答闭环

1. embedding 生成和向量检索。
2. 关键词、符号、向量三路召回及可解释排序。
3. 自然语言代码问答和证据引用。
4. 引用代码预览。
5. 基础 caller / callee 查询。

### 8.3 M2：图分析和知识沉淀

1. 多层调用图和影响分析。
2. 增量索引。
3. 知识卡片和 FAQ 沉淀。
4. 多仓库联合检索。

暂不做：

1. 企业级权限。
2. 多模型路由。
3. 复杂知识卡片工作流。
4. 自动代码修改。

## 9. 验收用例

1. 导入一个已有 CodeGraph 索引的仓库，系统能识别并读取索引。
2. 提问“某个函数做什么”，系统返回函数说明和代码引用。
3. 提问“某个函数被谁调用”，系统返回调用方列表。
4. 提问“某个功能在哪里实现”，系统通过 RAG 找到相关代码。
5. 提问“修改某函数有什么影响”，系统返回调用链和建议验证范围。
6. 索引任务失败时，用户可以看到失败阶段和错误信息。

## 10. 待确认问题

以下内容尚不能仅凭当前材料确定。每项给出推荐默认值，确认前按默认值开发，避免阻塞 M0。

| 决策项 | 推荐默认值 | 选择影响 |
| --- | --- | --- |
| 部署形态 | 单机本地 Web 服务 | 本地路径导入只在服务与仓库位于同一台机器时成立；内网部署需要服务端目录白名单或上传/克隆流程。 |
| 仓库来源 | 支持本地 Git、远程 Git、GitLab 和 ZIP | 远程来源需要凭据托管与同步策略；ZIP 没有 commit，必须使用上传版本和文件摘要保证可追溯。 |
| 用户与登录 | M0 单用户，不启用后端鉴权；登录页作为预留界面 | 若首期必须真实登录，需要提前加入用户存储、密码策略、会话和接口鉴权。 |
| CodeGraph 生成责任 | 平台负责调用受支持版本的 CodeGraph CLI | 需要固定兼容版本，执行环境预检，并实现超时、日志、资源限制、版本化产物和失败恢复。 |
| 外部模型 | 默认禁用，管理员显式配置后启用 | 启用前必须展示发送范围并过滤敏感文件；否则采用本地模型。 |
| 首批语言 | Java、TypeScript、Python | 实际支持粒度取决于 CodeGraph 对各语言的符号和调用边质量，应以测试样例验收。 |
| 问答语言 | 中文提问，保留英文代码标识符；支持英文提问 | 不要求答案自动双语输出。 |
| 数据库 | 开发期内存/SQLite，M1 前确定 PostgreSQL + pgvector | 向量索引进入主流程后再迁移会增加数据迁移成本。 |
| 仓库规模 | M0 基线 10 万行，单仓库小于 2 GB | 更大规模需要流式扫描、任务分片和独立 worker。 |
| 多仓检索 | 默认一次只选择一个仓库 | 跨仓符号冲突、权限和排序需单独设计。 |
| 知识卡片 | M2 再启用，保存前需人工确认 | 自动沉淀容易把错误答案持续注入检索。 |

## 11. 已补充的业务规则

### 11.1 仓库导入

1. 仓库来源统一建模为 `LOCAL_GIT`、`REMOTE_GIT`、`GITLAB`、`ZIP`，创建后来源类型不可直接修改；需要变更来源时新建仓库。
2. 本地 Git 路径必须存在、可读且为 Git 仓库；规范化后必须位于服务端允许根目录内。同一规范化路径只能登记一次。
3. 远程 Git 支持 HTTPS 和 SSH 地址，必须指定默认分支。系统克隆到受管目录，不允许用户在受管副本中直接修改代码。
4. GitLab 来源通过项目地址或项目 ID 接入，支持 Personal/Project Access Token；令牌加密保存且接口、日志和页面只显示掩码。
5. 远程 Git 和 GitLab 同一项目、同一分支默认只能登记一次；如需同项目多分支，必须创建独立仓库记录。
6. ZIP 上传必须提供仓库名称；默认分支和 commit 不适用，使用 `upload_version`、ZIP SHA-256 和解压后内容摘要标识代码版本。
7. ZIP 仅允许一个有效源码根目录。若压缩包包含单一顶层目录，系统自动剥离该目录；不得依赖压缩包文件名判断仓库身份。
8. 所有来源均写入平台受管的代码快照目录；本地 Git 只登记原路径，不复制和删除用户原目录。
9. Git 来源明确展示 branch、commit 和工作区修改状态；ZIP 来源展示上传版本、文件摘要和上传时间，不伪造 Git 元数据。
10. 符号链接不得越过允许根目录；默认不处理 Git submodule 和 Git LFS 实体内容。
11. `.codegraph/` 缺失不阻止仓库创建，但状态为“待生成 CodeGraph”，结构化检索不可用。

### 11.2 仓库同步与 ZIP 覆盖

1. 本地 Git 的“同步”只重新读取当前文件、branch、commit 和工作区状态，不执行 `pull`，避免修改用户目录。
2. 远程 Git 和 GitLab 的“同步”执行 `fetch` 并将受管副本更新到远端指定分支最新 commit；受管副本不得保留本地修改。
3. 同步必须在临时目录或临时 worktree 中完成校验，再原子切换当前代码版本；认证失败、网络失败或检出失败不得破坏当前可用版本。
4. ZIP“重新上传”是同一仓库的新代码版本：仓库 ID、名称、权限和历史任务保留，当前受管代码目录由新包完整覆盖，而不是合并文件。
5. ZIP 覆盖采用“上传 -> 安全校验 -> 临时解压 -> 内容扫描 -> 原子目录切换”流程。任一步骤失败都保留原代码和原索引。
6. ZIP 覆盖成功后，旧代码快照进入可配置的短期回收期；当前索引立即标记“可能过期”，新全量索引成功前旧索引仍可查询并明确展示其对应旧版本。
7. 相同 ZIP SHA-256 重复上传视为幂等操作，不创建新版本，也不重复触发索引。
8. 禁止路径穿越、绝对路径、越界符号链接、设备文件和嵌套压缩包；限制压缩包大小、文件数、单文件大小、解压总大小和压缩比，防止 ZIP Bomb。
9. 同一仓库同一时刻只允许一个同步或 ZIP 覆盖任务；同步与索引互斥，代码版本切换后再创建索引任务。
10. 自动同步和 GitLab Webhook 暂不作为默认能力；首期提供手动同步，后续可增加定时任务和签名校验后的 Webhook。

### 11.3 CodeGraph 分析任务

1. CodeGraph 分析状态统一为 `NOT_GENERATED`、`QUEUED`、`RUNNING`、`AVAILABLE`、`STALE`、`FAILED`、`INCOMPATIBLE`。
2. 仓库管理页提供“开始分析”“重新分析”“查看任务”和“查看错误”入口；不单独设置 CodeGraph 管理菜单。
3. 分析任务阶段至少包括环境预检、扫描源码、识别语言、解析符号、建立引用、建立调用关系、写入产物和结果校验。
4. 执行前检查 CLI 是否安装、版本是否受支持、代码目录是否可读以及资源配额是否满足；预检失败不得进入分析阶段。
5. 同一仓库同一时刻只允许一个代码变更、CodeGraph 分析或知识索引任务；任务按“同步/覆盖 -> CodeGraph -> 知识索引”串行执行。
6. CodeGraph 产物在临时目录生成并通过最小 schema 和查询抽样校验后再发布；失败时保留上一版可用产物。
7. 产物必须记录 `repository_id`、代码版本、CodeGraph CLI 版本、schema 版本、生成时间和内容摘要。
8. 代码版本发生变化后，现有产物标记为 `STALE`；允许查看旧结构事实时必须明确标注其对应旧代码版本。
9. 任务支持超时、取消和从头重试；完整日志写入服务日志，页面展示阶段、进度和脱敏错误摘要。
10. 添加仓库时提供“导入后自动分析并建立索引”选项，默认关闭；开启后按串行流程自动创建后续任务。

### 11.4 知识索引任务

1. 同一仓库同一时刻最多有一个运行中的索引任务；重复触发返回当前任务。
2. 状态统一为 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELED`；M0 可暂不实现取消操作，但数据模型需保留状态。
3. 进度必须包含当前阶段、已处理数量、总量（可获知时）、开始时间和最近更新时间。
4. 索引产物必须绑定代码版本和 CodeGraph 产物版本；Git 使用 commit 和工作区快照，ZIP 使用上传版本和内容摘要。任一依赖变化后标记为“可能过期”。
5. 全量索引采用新版本构建成功后切换的策略；失败任务不得破坏上一次可用索引。
6. 失败信息面向用户展示摘要，完整堆栈仅写入服务日志；允许从头重试。

### 11.5 删除语义

1. “删除仓库”删除平台记录、chunk、embedding、任务记录、缓存及平台受管的远程 Git/GitLab/ZIP 代码副本；不删除本地 Git 原目录及其中的 `.codegraph/`。
2. 删除操作必须二次确认，并明确列出会删除和不会删除的数据。
3. 运行同步、ZIP 覆盖、CodeGraph 分析或知识索引任务时不允许直接删除；应先取消任务，或等待任务结束。

### 11.6 检索、问答和引用

1. 引用最少包含 `repository_id`、commit、文件路径、起止行、符号名和证据类型。
2. 答案中的事实必须能映射到至少一个引用；无证据时返回“未找到足够证据”，不得仅依赖模型常识回答仓库事实。
3. 调用关系以 CodeGraph 为准；语义检索只能补充说明，不得覆盖结构事实。
4. 默认只在当前选中仓库和已发布的索引版本内检索，避免混用不同 commit 的证据。

### 11.7 敏感数据

1. 默认排除 `.env*`、私钥、证书、凭据文件、压缩包、数据库文件和超过配置阈值的单文件。
2. 排除规则需支持全局配置和仓库级补充，规则变更后提示重新索引。
3. 调用外部 embedding 或 LLM 前执行同一套过滤，并记录 provider、模型、发送字符数和调用时间，不记录明文代码正文。

## 12. 量化验收基线

1. M0 测试仓库基线：10 万行以内、2 GB 以内、文件数 2 万以内。
2. 仓库列表和详情接口在 100 个仓库记录内，服务端 P95 响应时间小于 500 ms。
3. 已完成索引上的关键词/chunk 查询，P95 响应时间小于 2 秒。
4. M1 纯结构图查询深度不超过 3、节点不超过 500 时，P95 小于 2 秒。
5. M1 问答首个可见状态应在 2 秒内返回；完整回答目标小于 10 秒，不含模型供应商异常。
6. 对验收问题集，100% 的仓库事实陈述带引用；无效文件路径和越界行号为 0。
7. 索引失败后，上一次成功索引仍可查询，且失败阶段和可操作错误摘要可见。
