项目已形成以“接入项目、准备分支、建立索引、维护知识、联合检索、回到来源”为主线的软件系统，交付内容覆盖前端工作台、后端服务、数据库结构、MCP 接入、质量评测样本及部署脚本。系统将代码位置与团队知识置于同一个查询入口，并通过分支、内容版本、提交和知识修订标识，帮助开发者核对信息来源。当前成果支持开展阶段性结项；生产运行效果和部分外部依赖能力仍需在目标环境中继续验收。

一、项目背景

1.1 建设背景

随着软件项目规模扩大，代码、设计说明、业务规则和运维经验往往分散在不同位置。开发人员查找问题时，既需要找到实现代码，也需要了解实现背后的约束和历史原因。仅依靠文件搜索或关键词匹配，通常难以把业务术语、代码符号与团队知识联系起来。

同时，项目持续迭代会带来多分支、多提交和文档更新不同步的问题。某条知识可能适用于主分支，却不适用于维护分支；某个历史回答引用的代码，也可能已经在后续提交中变化。缺少明确版本信息时，使用者难以判断结果是否适用于当前工作范围。

AI 辅助开发进一步增加了对可靠上下文的需求。回答即使表达完整，如果缺少源码位置或知识原文依据，开发人员仍需要重新核实。项目因此围绕“查到实现、理解约束、核对来源”开展建设，为人工阅读和 AI 工具提供可追溯的项目上下文。

1.2 建设目标

本项目的建设目标主要包括：

  1. 建立统一的代码与知识检索入口，使一次查询能够同时返回代码片段和相关知识。
  2. 将查询和阅读限定在明确的项目、分支及内容版本内，减少版本混用。
  3. 通过知识卡沉淀业务规则、架构决策、数据约束、运维经验等团队知识。
  4. 为检索结果和问答保留可核对的文件、行号、提交及知识修订信息。
  5. 提供权限控制、任务管理和部署交付能力，支持团队协作与私有环境部署。
  6. 通过标准化 MCP 接口，让外部 AI 客户端能够在授权范围内读取项目证据。

1.3 项目定位与服务对象

Analyzer Coder 定位为面向开发者的代码与知识联合检索平台，主要服务于软件开发、测试、项目维护及技术管理人员。典型应用场景包括新成员熟悉项目、业务实现定位、缺陷排查、技术交接和项目知识维护。

当前核心功能围绕单个项目及其分支展开。代码图谱提供结构关系与影响线索，平台通过只读方式使用受管代码内容，不承担自动修改代码、提交变更或自动执行发布审批的职责。

二、项目功能介绍

2.1 项目接入与管理

系统支持本地 Git、远程 Git、GitLab 和 ZIP 等代码来源，并提供项目资料、来源凭据、成员权限及项目生命周期管理。平台中的“项目”是接入和管理的逻辑对象，仓库是其代码来源。

多种接入方式覆盖了不同使用条件：具有版本管理的项目可按 Git 分支进行准备；仅有源码压缩包的项目也可以导入，ZIP 来源使用固定逻辑分支 WORKSPACE。

2.2 分支准备与版本化阅读

系统管理项目下的受管分支，并提供同步、内容索引和图谱构建等准备操作。分支代码以受管内容版本保存，阅读上下文记录项目、分支、内容版本和提交信息。

使用者切换分支后，检索、源码查看、问答和图谱读取依据相应上下文执行。未准备的分支会显示明确状态，相关读取不会静默借用其他分支的产物。这一机制为多分支项目提供了可核对的阅读范围。

2.3 代码索引与向量索引

后端扫描受管代码，按支持的文件类型、忽略目录和文件大小规则筛选内容，再切分为可检索片段。片段记录文件路径、符号及起止位置，支持检索结果跳转回源码。

索引能力覆盖 Java、TypeScript、JavaScript、Python、Go、Vue 等多种代码文件，以及 Markdown、SQL、配置文件等文本资产。支持纳入索引并不表示所有语言都具有同等深度的语义分析能力。

向量索引作为增强能力，可接入外部 embedding 模型，并提供索引覆盖情况。未配置外部模型时，系统仍保留关键词与字符相似度检索路径；字符相似度用于文本匹配，不等同于完整语义理解。

2.4 代码与知识联合检索

“联合检索”是项目的核心入口。用户可以输入类名、函数名、错误信息或业务术语，在同一结果列表中查看代码片段和知识卡。

检索根据当前能力组合关键词与向量通道，对候选结果去重并融合排序，返回来源类型、相关度及检索诊断信息。代码结果保留文件路径和位置，知识结果可回到卡片原文及修订信息。具体通道的启用条件受模型配置和阅读范围限制，系统会说明降级原因。

2.5 知识卡管理

知识卡用于保存代码之外的工程共识，支持标题、Markdown 正文、标签、附件及关联代码，并可描述业务规则、架构决策、安全要求、数据约束、运维手册等内容。

系统提供草稿、评审、发布、撤回、归档及历史恢复流程。当前界面通过“确认并发布”整合评审与分支确认操作；正式发布仍受后端权限和知识状态约束。编辑知识卡生成新修订，历史内容可恢复为新的草稿。

当前实现支持仅当前分支、项目共享和指定分支共享。共享卡片维护同一份正文，分支验证结论分别记录。知识可绑定源码片段、路径和符号；当来源代码变化时，系统提供来源漂移提示与复核入口，帮助维护者判断知识是否仍然适用。

2.6 基于证据的项目问答

项目问答以联合检索材料为依据，返回回答及代码、知识引用，并保存按账号隔离的会话历史。使用者可以展开证据、查看来源，再跳转到对应源码或知识卡。

系统支持外部聊天模型，也提供无需外部模型的本地证据模式。本地模式返回基于已有检索材料的确定性回答，并明确标注降级状态。引用帮助用户核实结论，回答质量仍需结合实际问题和证据进行评估。

2.7 代码图谱与关系浏览

系统可构建绑定到分支内容版本的 CodeGraph 产物，并通过代码图谱页面浏览节点、关系与源码位置。前端包含二维和三维展示组件，辅助理解项目结构、调用关系和符号影响范围。

图谱和 MCP 工具还可提供调用方、被调用方、文件及受影响测试的关联线索。这些结果来自静态分析，不能直接代表运行时真实调用链，也不能替代测试执行结果。

2.8 账号、权限与审计

系统区分超级管理员和普通账号，并提供项目级 READ、MAINTAIN、MANAGE 三级权限及所有者关系。服务端对读取、维护和管理操作实施授权校验。

账号管理包含登录会话、验证码、账号锁定、密码重置和强制改密等能力；审计记录用于追踪相关操作。账户访问令牌用于 MCP 等读取场景，与 Git 或 GitLab 来源凭据分别管理。

2.9 任务中心与模型配置

代码索引、分支准备、向量及图谱构建等操作由后台任务执行。任务界面展示状态、阶段及失败信息，并为支持的任务提供取消或重试入口，方便维护者识别并处理准备失败。

模型配置支持聊天和向量模型的设置及连通性检测。外部服务不可用时，系统尽量维持基础检索和来源阅读，并显示相应状态。

2.10 MCP 接入与部署交付

Java 后端提供 /api/mcp 只读 Streamable HTTP 服务；仅支持 stdio 的客户端可通过 Node.js 适配器接入。工具覆盖项目与分支发现、阅读上下文解析、联合检索及代码图谱查询，调用时校验令牌和项目读取权限。

项目提供分离式发布包和一体化 Docker 交付方案，包含构建、启动、健康检查及校验脚本。当前工作区已有 1.0.0 分离式发布目录和 linux/amd64 一体化镜像导出目录，可作为部署交付资产；目标环境中的运行与升级效果仍需结合实际配置验收。

4.3 关键实现难点与处理

分支与证据一致性。 系统以项目、分支、内容版本和提交作为阅读坐标，将代码索引、图谱及引用绑定到相应版本，并通过上下文校验减少不同范围材料混用。

代码与知识的统一检索。 两类内容采用共同的证据返回结构，通过多通道召回、去重和融合排序进入统一结果列表，同时保留各自的来源位置和状态。

知识共享与独立有效性。 共享卡片维护一份正文，分支验证分别记录；编辑提交修订信息以识别并发冲突，历史恢复带回相关内容、范围及引用，随后重新确认发布。

增强能力失败时的可用性。 外部模型、向量和图谱能力具有独立状态及降级说明，基础检索和来源查看尽量不依赖全部增强组件同时可用。

界面操作的连续性。 近期前端优化覆盖输入失败后的保留与重试、源码和证据对照、跨分支来源往返、详情关闭后的焦点恢复，以及小屏布局和键盘操作。

五、项目优点

5.1 围绕开发者的实际查询流程

平台将“查找代码”和“理解规则”连接在一起，使用者可以从业务术语进入检索，再从结果回到源码或知识原文。核心使用路径集中，便于围绕高频场景持续改进。

5.2 来源与版本信息清楚

代码结果、问答和知识引用保留来源坐标，分支上下文明确当前阅读范围。这为历史问题复查、多分支维护和技术交接提供了更可靠的信息基础。

5.3 知识能够持续维护

知识卡包含修订、评审、发布、来源复核和历史恢复机制，并将共享范围与分支验证分别管理。团队可以维护知识的适用性，而不仅是持续增加文档数量。

5.4 基础能力对外部模型依赖较低

关键词检索、字符相似度和本地证据模式使基础路径在未配置外部模型时仍可使用。组织可先部署检索与知识维护，再按实际需要增加模型能力。

5.5 团队使用与工具接入能力较完整

项目级权限、来源凭据、账户访问令牌、任务状态和审计能力，为多人使用提供基础治理机制。只读 MCP 接口则让人工工作台与外部 AI 客户端能够复用相同项目证据。

5.6 工程交付与验证资产较齐备

项目同时具备源码、测试、专项验收记录、部署包和运行手册。近期界面优化也关注了失败恢复、响应式布局和键盘操作，降低了功能之间衔接的使用成本。

这些优点体现了当前方案的设计与实现价值。实际吞吐量、响应时间、团队效率改善和用户满意度，仍需通过持续运行和用户反馈验证。

六、项目展望

6.1 近期：补齐真实环境验收与发布闭环

优先使用独立测试项目完成 Git/ZIP 接入、分支准备、知识发布、检索、问答、附件和 MCP 客户端的完整联调。针对外部模型、真实 Git/GitLab 来源和目标设备三维渲染，补充可重复的验证记录。

同时，在目标服务器验证 Linux 启动、HTTPS、备份恢复、历史数据升级及长期运行。对当前发布流程，应补齐实际质量结果文件的生成或交付步骤，使已有质量门禁能够在发布时执行。

6.2 近期至中期：形成可量化的检索质量结论

项目已有47条检索和26条问答样本，并配置了前10条召回率不低于85%、引用覆盖率不低于95%、陈述支持率不低于90%、P95延迟不高于5000毫秒的目标门槛。这些数值是评测目标，当前不能写作已达到的性能成果。

后续应基于真实运行结果和具名人工评审，补充完整评测报告；再按查询类型、语言、项目规模和模型配置分析不足，改进排序、中文术语匹配及向量覆盖。

6.3 中期：提升规模化使用能力

在具有实际容量数据后，优化增量索引、任务调度、向量查询和图谱展示，重点关注大仓库、多分支准备及多人同时检索的资源消耗。

前端生产构建已有较大分包提示，可继续完善按需加载和资源拆分，并建立运行监控、任务积压观察和备份演练机制，使运维问题更容易发现和恢复。

6.4 中期：加强知识维护与协作体验

围绕真实团队需求，探索知识模板、批量维护、来源变化提醒和维护责任机制，并完善共享卡片在不同分支上的验证体验。持续检查历史恢复、并发编辑、附件管理及权限入口的一致性。

还应同步更新文档与实现，统一知识范围、迁移规则和 MCP 工具目录，减少使用者因不同资料描述不一致而产生的理解成本。

6.5 长期：深化开发工具集成

在保持来源可追溯和权限约束的基础上，扩展 IDE、企业知识工具及更多 AI 客户端的读取体验，让开发者在常用工作环境中获取代码和知识证据。

跨仓聚合、服务契约关联或更深层次分析可作为后续需求研究方向，应先确认用户场景、数据边界和验证方法，再决定是否纳入产品范围。

6.6 阶段结项评价

Analyzer Coder 已形成代码与知识联合检索的主要功能链路，并具备版本化阅读、知识治理、证据问答、图谱浏览、权限控制及工程交付资产。现有专项记录为阶段成果提供了验证依据。

本阶段可以按已实现功能、源码、文档、部署资产和专项验证进行交付归档。后续工作的重点是补齐目标环境验收、量化检索效果，并依据真实使用情况持续优化稳定性与协作体验。
