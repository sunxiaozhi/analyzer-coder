# 多分支代码与共享知识设计方案

状态：实施中，已接入本地 Git 分支快照、独立分支检索窗口、知识范围管理与 MCP 上下文；尚非全部方案完成。更新：2026-09-14。

当前交付边界：

- 标签栏新增“分支工作区”：显式添加本地分支、准备/更新快照、锁定阅读版本、检索该分支代码和适用知识。不会改变其他页面的默认快照。
- 知识卡片的“适用分支”支持所有分支共享或指定分支；选择一个即仅对该分支适用。范围修改生成新修订，保留引用和附件，不复制验证状态。
- HTTP 与两种 MCP 接入均可复用 `contextId`；读取未准备分支或携带上下文访问未支持接口时明确拒绝，不静默回退。
- 目前只导出已有本地 Git 分支的提交；远程发现/拉取、异步准备任务、分支向量构建、分支 CodeGraph 构建、全站统一分支切换与 Markdown 来源分支化仍待接入。分支关键词检索可用；缺失向量索引会报告降级。
- 分支验证已有维护 API，尚未提供完整的人工验证界面；有代码引用或执行要求的知识未在该分支快照验证前不会进入分支检索。
- V3 迁移已在开发库回滚事务中试跑；实际应用以部署时 Flyway 执行为准，不手工改写迁移历史。

## 1. 目标与边界

在一个项目中管理多个代码分支，让人与 Agent 在明确的代码版本下使用共享知识，同时能够表达分支差异。

核心约定：**仓库是知识的归属，分支是适用范围，快照是代码证据的版本，知识修订是正文的版本。**

- 首期将现有 `repositoryId` 对应的仓库作为界面中的项目，不为每个分支复制仓库或权限。
- 已有工程项目相关模型不与本次“项目”混用；跨仓库工程知识聚合不纳入首期。
- 保留现有源码检索、知识卡片、问答、代码图谱、Markdown 来源和 MCP 入口。
- 不修改用户工作目录的 Git 分支，不替用户提交、合并或删除远程分支。
- 首期只支持显式选择分支；不做通配符分支范围、按 Git 祖先自动继承知识或自动合并知识正文。

## 2. 现有实现依据与关键差距

以下为实施前的工作区源代码检查结果。现已只读核验开发库迁移历史为 V1、V2，并完成 V3 回滚试跑。

| 当前实现 | 对多分支的影响 | 改造方向 |
| --- | --- | --- |
| `CodeRepository` 与 `RepositoryMapper.xml` 在仓库上保存一套 `currentSnapshotId/currentCommit/codeGraphPath` | 分支切换可能覆盖仓库级当前版本 | 增加分支级已发布快照指针，仓库只保留默认分支 |
| `IntelligenceMapper.xml`、`CodeChunkMapper.xml` 多处从仓库查询当前快照 | 只加前端分支选择不能实现检索隔离 | 查询统一接收已解析的快照 ID |
| `CodeChunkMapper.xml` 有按仓库/路径删除、给未变化片段改写快照 ID 的操作 | 不能直接用于并存的分支快照，可能删除或重写别的分支证据 | 按快照创建独立成员记录，删除必须明确快照范围 |
| 知识卡片已有修订、引用、审核与代码有效性字段 | 可以复用知识资产，但卡片级有效性不足以表达分支差异 | 正文修订继续复用，验证结果独立到修订×分支×快照 |
| `KnowledgeScope` 已描述路径、符号、模块等范围 | 分支适用性与代码路径范围不是同一维度 | 分支选择器独立建模，不把分支名塞进路径条件 |
| `MarkdownKnowledgeSourceService` 按仓库当前扫描同步来源 | 相同路径在不同分支可能相互覆盖 | 来源身份增加分支与快照 |
| `McpToolService` 当前 `search_project` 接收仓库、查询词与数量 | Agent 无法锁定明确分支版本 | 增加分支上下文解析及后续复用 |

## 3. 用户可见功能

### 3.1 分支上下文

顶部保留“项目”选择，旁边增加“分支”选择；提交号与索引状态使用紧凑状态展示。

- 默认进入默认分支；可以记住个人最近选择，但通过 URL 打开的明确分支优先。
- 分支列表显示分支名称、最新发现提交、当前已发布提交、索引状态。
- 只对用户选择跟踪的分支创建索引；发现远程分支不等于索引全部分支。
- 选中未索引分支时显示“尚未准备”，提供准备操作，绝不展示默认分支的代码冒充结果。
- 构建新版本期间继续提供该分支上一次成功发布的版本，明确标注“有更新待发布”。
- 不自动切换正在阅读的快照，用户点击刷新/更新上下文后切换。

### 3.2 知识适用范围

创建和编辑知识卡片时，只增加三个选项：

| 界面选项 | 实际存储 | 默认建议 |
| --- | --- | --- |
| 当前分支 | `SELECTED_BRANCHES` + 当前 branchId | 代码生成、问答提炼、仓库 Markdown 导入默认选择 |
| 项目共享 | `ALL_BRANCHES` | 手工确认的通用术语、流程和规范可主动选择 |
| 指定分支 | `SELECTED_BRANCHES` + 非空 branchId 集合 | 多个发布分支共同适用的知识 |

“当前分支”保存的是确定的分支 ID，之后切换页面不会改变这条知识的范围。

“项目共享”自动适用于未来新增分支，但**适用不等于在所有分支验证通过**。有代码依据的共享知识，在新分支中仍可能显示“未验证”。

知识列表默认展示当前分支有效视图；管理者可切换“全部范围”维护卡片，其他分支卡片明确标记，不直接加入当前问答。

### 3.3 分支覆盖

在共享知识上提供“为当前分支创建差异版本”。系统建立显式覆盖关联，不靠标题相同推断。

例：共享《鉴权接入规范》使用统一鉴权组件，`feature/new-auth` 的差异版本描述迁移约束。该分支使用差异版本，其他分支继续使用共享版本。

- 差异版本为同一知识主题的完整替代正文，首期不做段落补丁合成。
- 共享版本更新不会自动重写差异版本，只提示其基线发生变化。
- 将差异版本推广为共享版本需要预览受影响分支并人工确认。
- Git 分支合并不自动推广或归档知识；代码合并和知识发布是两项独立操作。

## 4. 概念模型与建议数据结构

以下为建议逻辑模型，字段命名可在实施时对齐现有持久化规范。

| 实体 | 关键字段 | 约束与作用 |
| --- | --- | --- |
| 现有 `repositories` | id、default_branch_id、来源与权限字段 | 默认分支不再承担全仓库版本指针语义 |
| 新增 `repository_branches` | id、repo_id、ref_name、ref_kind、tracking_status、head_commit、published_snapshot_id、generation | 活跃分支的仓库+完整 ref 唯一；稳定 ID 避免按显示名称关联 |
| 新增 `repository_snapshots` | id、repo_id、branch_id、commit_sha、worktree_digest、dirty、source_path、source_status、created_at | 只读内容版本；脏工作区不能伪装成纯提交版本 |
| 新增快照能力清单 | snapshot_id、capability、artifact_id、build_fingerprint、status | 分别记录 chunks、vectors、codegraph 等产物，防止跨版本拼接 |
| 扩展 `index_jobs` | branch_id、target_snapshot_id、expected_generation、能力、幂等键 | 构建任务绑定确定输入；不同分支任务互不覆盖 |
| 扩展知识修订 | family_id、branch_scope、origin_branch_id、overrides_card_id、based_on_shared_revision | 范围与覆盖关系也必须随正文一起进入不可变修订历史 |
| 新增知识修订适用分支表 | card_id、revision、branch_id | 与修订联合关联；分支必须属于同一仓库 |
| 新增 `knowledge_branch_validations` | card_id、revision、branch_id、snapshot_id、state、reason、checked_at、checked_by | 每次验证绑定正文与代码版本；不得用一个全局 CURRENT 代替 |
| 扩展知识来源/引用 | repo_id、branch_id、snapshot_id、path、symbol、range、content_hash | 原始证据只读保留；目标分支重新定位另存映射，不覆盖原引用 |
| 新增短期阅读上下文 | id、repo_id、branch_id、snapshot_id、knowledge_revision_set、expires_at | 服务端保存固定知识修订集合，返回不透明 contextId |

首期一个快照归属一个分支，不跨分支复用 snapshotId。即便提交相同，也仅在后续复用底层内容，避免提前引入多对多生命周期复杂度。

`ref_kind` 区分 Git 分支、显式本地工作区或导入来源。无 Git 来源不伪造 `main`；先保持单一“导入版本”上下文。用户本地脏目录只作为明确的本地工作区版本，不发布为远程分支已提交内容。

## 5. 快照创建、构建与发布

1. 校验仓库权限、分支身份和来源；解析分支到确定 commit，后续步骤不再重复使用可移动分支名读取代码。
2. 在受管目录创建隔离只读内容，记录来源及摘要；不得在用户工作目录执行 checkout/reset。
3. 从同一快照创建内容片段；向量和 CodeGraph 可异步构建，产物记录同一 snapshotId 与构建指纹。
4. 基础检索所需产物就绪后，通过分支 generation 的比较更新原子发布该分支指针。
5. 新版本索引失败不覆盖旧指针；过期任务即使晚完成也不能覆盖后来成功发布的版本。
6. 新快照没有向量时允许关键词检索；没有 CodeGraph 时提示图谱待准备，不能借用旧快照图谱补齐。

状态不要混成一个布尔值：来源快照是否就绪、分支是否有新提交、各索引能力是否就绪分别记录。

增量更新必须创建新快照的成员记录。当前按仓库删除片段、修改旧片段 snapshotId、按路径删除旧内容的实现需要改造；旧问答引用的快照不能被原地重写。

## 6. 知识解析与检索规则

### 6.1 有效知识集合

统一通过 `EffectiveKnowledgeResolver` 处理网页检索、问答、MCP 和未来规则导出：

1. 验证请求账号对仓库与上下文的访问权限。
2. 选择已经发布且通过所需审核的知识修订。
3. 过滤分支适用范围；之后继续应用已有路径、符号、模块等范围条件。
4. 按 familyId 处理显式差异版本：适用的已发布覆盖版本替代共享基线。
5. 评估该修订在当前分支快照上的验证状态。
6. 在有效候选集合中做关键词/向量召回、融合排序和引用组装。

不能先在全分支取 Top K 再过滤，这既容易漏掉合法结果，也会让分支隔离依赖偶然排序。向量条目必须匹配正文 revision。

### 6.2 冲突与覆盖边界

- 同一 family 在同一分支最多有一个已发布差异版本；发布事务校验重叠范围并加锁，不能仅依赖前端检查。
- 草稿不影响现有有效版本；覆盖版本归档后，经明确操作恢复共享基线。
- 已发布覆盖版本失效时显示阻断/待复核状态，不能悄悄退回可能不适用的共享版本。
- 不同 family 的矛盾只标记为冲突候选，保留双方依据；首期不承诺自动发现所有语义冲突。
- 权限策略、安全控制等硬约束不能通过普通知识覆盖机制降级；必须遵循既有审批要求。

### 6.3 知识类型与有效性

| 状态 | 含义 | 默认问答/Agent 使用方式 |
| --- | --- | --- |
| `CURRENT` | 当前修订在目标快照完成适用性确认 | 可作为已验证知识；仍保留证据引用 |
| `UNVERIFIED` | 适用范围包含目标分支，但未验证其代码依据 | 普通参考可带明确标识，不能声称当前代码事实 |
| `REVIEW_REQUIRED` | 引用变化、基线变化或范围调整 | 默认不作为确定结论/可执行规则，给出待复核提示 |
| `INVALID` | 已确认与目标分支不符 | 排除有效知识集合，管理界面保留 |

无代码依据的通用流程按发布和审核状态使用，显示“不涉及代码验证”，不能为了凑状态标成 CURRENT。REQUIRED 类知识必须满足目标分支验证和审批条件；普通参考的宽松规则不适用于它。

代码引用哈希未变化只证明引用片段稳定，不自动证明全部语义仍适用；可保留“依据未变化”检查结果，但不得将另一个分支的人工验证复制过来。

## 7. 人与 Agent 的上下文一致性

引入服务端 `BranchContextResolver`，返回：

```json
{
  "contextId": "opaque-id",
  "repositoryId": "repository-id",
  "branchId": "branch-id",
  "branchName": "release/2.x",
  "snapshotId": "snapshot-id",
  "commitSha": "resolved-commit",
  "capabilities": { "chunks": "READY", "vectors": "PENDING", "codegraph": "READY" },
  "expiresAt": "server-defined-expiry"
}
```

- contextId 在服务端绑定代码快照和当时有效的知识修订集合，而不是只冻结代码、知识仍随时变化。
- 后续检索、图谱、文件读取和问答复用该上下文；返回引用包含知识 revision、分支与提交来源。
- 每次调用仍重新检查当前权限；知识撤回或访问撤销优先于上下文固定，不得以历史快照为由继续泄露。
- 上下文过期明确返回过期错误，用户或 Agent 显式刷新；不偷偷解析到最新快照。
- 已完成问答永久保存实际引用的知识修订与代码定位信息；不依赖短期 contextId 还存在。
- 问答过程中切换分支时提示开启新上下文；历史回答保留原标签，不作为新分支已验证事实。

## 8. 接口建议

沿用现有仓库路由和鉴权，不另建平行的项目 API。

| 接口/入口 | 建议扩展 |
| --- | --- |
| `GET /api/repositories/{id}/branches` | 返回已跟踪分支及各自准备状态 |
| 分支发现/跟踪/停止跟踪操作 | 独立管理动作；停止跟踪不删除远程分支，不立即清除引用数据 |
| `POST /api/repositories/{id}/branches/{branchId}/prepare` | 创建绑定分支的准备任务，返回 jobId 与 targetSnapshotId（已分配时） |
| `POST /api/repositories/{id}/contexts` | 指定 branchId，必要时指定属于该分支的保留 snapshotId，创建只读上下文 |
| 现有检索、问答、文件与图谱接口 | 增加 contextId；服务层与 Mapper 显式接收 resolved snapshotId |
| 现有知识创建/编辑/发布接口 | 增加分支范围与差异版本信息；预期 revision 防止覆盖并发编辑 |
| 知识验证接口 | 提交 cardId/revision/contextId，记录目标分支快照验证结果 |
| MCP `search_project` | 增加 branchId/contextId；首次调用解析并返回上下文，后续复用 |
| MCP 新增 `resolve_project_context` | 只读解析分支与快照，为不同 Agent 提供统一入口 |

兼容策略：旧客户端未带分支时只能解析默认分支，并在响应中明确返回实际上下文；请求显式指定不存在、无权或未准备的分支时不得回落。默认分支变化后新请求可使用新默认值，已有上下文不变。

错误须区分：分支不存在、分支未准备、产物待构建、上下文过期、版本不匹配、覆盖冲突。没有图谱不等于没有知识，不能将增强能力失败作为整个问答失败。

## 9. 页面交互改动

- 全局仓库栏：增加分支选择；提交和索引状态紧凑展示，详细信息放入状态展开区。
- 项目管理：增加“跟踪分支”，不把同仓库各分支重复成多个项目卡片。
- 知识编辑：适用范围三选一、分支多选、共享影响提示；共享知识提供创建当前分支差异版本入口。
- 知识列表：当前分支为默认筛选，卡片标签区分共享/分支专属/覆盖和当前验证状态。
- 图谱及代码：在原页切换分支；快照变更后清除旧选中符号、旧请求与缓存，保留明确的加载状态。
- 问答引用：简洁展示分支与提交，展开后查看原始证据来源和知识修订。
- 地址栏/页面标签保存 branchId/contextId，不能仅依赖全局可变 store；不同页签和并行 Agent 可使用不同分支。

前端缓存至少按 repoId、branchId、snapshotId、知识上下文版本区分；请求返回时校验上下文，避免快速切换造成旧结果覆盖。

## 10. 权限、生命周期与存储

- 首期继承现有仓库权限，**不承诺分支级保密隔离**。如果同仓库内存在受限分支，需要先增加分支 ACL，不能用知识范围代替授权。
- 共享知识不得直接扩大附件、来源文件或外仓库引用的可见性；所有引用仍需单独通过既有权限检查。
- 分支名是外部输入，只能经 Git ref 校验和安全参数传递；受管磁盘目录使用内部 ID，不把分支名直接拼成路径。
- 远程分支删除后停止同步并保留归档身份；同名分支重建不能不经确认继承原覆盖知识。
- 检测到重命名不能仅凭相同提交自动合并身份；提供显式确认。强制推送产生新快照，不改变旧证据。
- 第一阶段保留所有已发布快照与被引用版本，不开放自动物理清理；只清理明确失败且未引用的临时产物。
- 后续 GC 通过当前分支指针、活动上下文、任务、问答与知识引用共同计算可回收对象，先归档再延迟清理。
- 后续内容去重键包含内容摘要和处理版本；向量还包括模型、维度、切片策略。相同文件内容不能直接复用全仓库语义图。
- 共享更新、差异发布、适用范围变更、分支停止跟踪应记录实际持久化结果的审计事件。

## 11. 存量数据迁移

1. 盘点实际数据库与已执行迁移，先解决 schema/Mapper 差异。通过新的前向迁移实现，不改写已执行的 V1/V2。
2. 每个现有仓库创建一个受管分支记录，承接当前跟踪 ref；导入来源使用显式非 Git 上下文。
3. 将现有当前快照、产物和片段登记到该分支；迁移前后数量、摘要与原查询结果对账。
4. 旧知识默认映射到原跟踪分支，而不是全部变成共享，避免自动扩大语义适用范围；后续提供批量确认共享。
5. 仅在原分支与原快照上迁移能够证实的验证结果；无法还原的来源保留为未验证。
6. 增加分支感知读写路径并进行影子对比；先跑通原单分支，再启用第二分支。
7. 仓库级旧版本字段在过渡期只能镜像默认分支，不能随用户切换更新；清除旧查询依赖后再退役。
8. 发生问题时通过功能开关关闭多分支入口，但不能让旧写入器重新运行仓库级清空逻辑。回退保留新增数据，并暂停不兼容写入。

## 12. 开发顺序与验收门槛

| 阶段 | 必须交付 | 验收门槛 |
| --- | --- | --- |
| P0：基线核对 | schema 对账、当前快照读写/清理调用点清单、迁移回退方案 | 明确所有仓库级覆盖/删除路径，不允许直接带入多分支 |
| P1：分支底座 | 分支记录、不可变快照、能力清单、原子发布、上下文解析；改造检索/源码/图谱读链路 | 两分支可同时准备和阅读，绝不串分支；失败保留旧可读版本 |
| P2：共享知识 MVP | 三种界面范围、版本化适用关系、分支验证状态、统一有效知识解析、网页与 MCP 上下文 | 共享只存一份；专属不泄漏；同条知识在两个分支可有不同验证状态 |
| P3：差异版本 | 显式覆盖、重叠发布约束、基线更新提示、推广共享流程 | 覆盖仅影响指定分支，冲突和失效不静默回退 |
| P4：运行优化 | 内容/向量去重、受控索引并发、分支归档与引用安全 GC | 节省资源且不破坏历史引用；不因缓存复用改变权限或版本 |

第一版范围收敛到 P0–P2，已经能解决“一个项目多分支、共用一部分知识”。暂不加入分支对比页面、自动语义冲突检测、自动知识合并和复杂代码城市联动。

### 必须覆盖的测试场景

1. main 与 feature 同路径内容不同：源码、关键词、向量、图谱均使用请求快照。
2. 共享规范两分支均可见，main 专属在 feature 不出现；新增分支不自动继承已有验证结果。
3. 未索引分支明确提示；不返回默认分支结果；缺少图谱时仍可检索已就绪内容。
4. 两个任务乱序完成、重复执行或发布失败：分支指针不倒退、不覆盖其他分支。
5. 发布期间执行长问答：一轮所有代码证据与知识修订一致；后续显式刷新才变更。
6. 更新 main 的依据：只影响相关修订的对应验证状态，不能把 feature 全部知识判为失效。
7. Markdown 同路径跨分支内容不同，来源独立；内容相同也不自动扩大知识适用范围。
8. 显式覆盖、重叠范围并发发布、覆盖失效、共享基线变化分别有确定行为。
9. 权限撤销或知识撤回后，旧 contextId 不能继续提供受限内容。
10. 删除/重建同名分支、强制推送、来源为脏工作区时，不错误复用分支身份和验证结果。
11. 历史问答及知识引用不因新分支发布、增量索引或清理而改变内容。
12. 存量迁移前后单分支查询结果一致；快速切换分支时旧响应不能污染新页面。

## 13. 方案结论

基于现有系统增量改造，不重新开发整个平台；但必须先解除“一个仓库只有一个当前版本”的底层约束。

产品上只增加分支上下文、知识适用范围和后续差异版本。技术复杂度主要留在统一上下文、不可变快照、检索隔离和分支验证内部，不把这些全部变成用户需要配置的功能。
