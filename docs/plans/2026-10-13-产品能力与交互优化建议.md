# 代码智库：产品能力与交互优化建议（第一版）

编写日期：2026-10-13｜依据：当前工作区代码，VERSION 1.1.3｜状态：U1–U5、U7 已实施，其余建议待讨论

2026-10-14 更新：已完成 MCP 指南、问答模式选择、编辑关闭保护、概览问题筛选四项修正。实施范围和验证口径见[交互修正验收记录](../qa/2026-10-14-交互修正验收.md)。下文的“现状”保留最初排查结果。

当前系统已覆盖项目接入、分支隔离、知识维护、联合检索、问答、代码图谱、MCP、权限与离线部署。下一步最有价值的方向，是让知识能从日常使用中积累、有人持续维护，并用于项目交接和改动判断。

本版基于源码核对和既有验证记录，未进行新一轮用户访谈、浏览器全流程测试或性能测量。下文区分“代码可确认的缺口”和“需要试点验证的产品建议”；收益均为预期。

**建议先做：修正高频交互 → 问答沉淀知识 + 复核工作台 → 按使用场景扩展影响核查或文档入库。**

2026-10-14 体验优化：补齐总览任务进度、完成刷新与继续使用入口（U5），以及搜索提示和零结果操作（U7）；同步优化图谱范围、编辑冲突、列表分页、长问答等待和附件说明。范围及边界见[使用体验优化验收](../qa/2026-10-14-使用体验优化验收.md)。

## 二、六项值得提升产品价值的能力

P0：优先修正使用障碍；P1：优先建设的产品增量；P2：按试点需求推进。投入 S/M/L 为相对规模，不代表排期：S 主要涉及局部界面或接口，M 涉及前后端流程，L 涉及新的数据处理或跨模块机制。

| 编号 | 建议能力 | 解决的问题 | 第一版交付范围 | 适用模式 | 优先级 / 投入 |
| --- | --- | --- | --- | --- | --- |
| F1 | **问答一键沉淀为知识** | 回答留在个人会话中，团队下次仍需重新查找 | 选中一轮回答 → 编辑草稿 → 保留问题、引用及来源版本 → 人工确认发布 | 两种模式 | P1 / M |
| F2 | **知识维护工作台** | 已能发现待复核知识，但处理入口分散，缺少连续处理流程 | “待我复核、未发布、缺负责人”清单；查看原因 → 处理 → 下一条；再补负责人分派与到期复查 | 两种模式；代码漂移仅代码项目 | P1 / M |
| F3 | **改动影响核查单** | 能查调用关系，但开发者仍需自己拼接影响范围、业务规则和测试线索 | 输入文件或符号 → 汇总静态影响、关联知识、维护人及检查项 → 导出核查单 | 代码项目 | P2 / M–L |
| F4 | **项目交接与场景手册** | 信息分散，新成员不知道先读什么 | 从现有项目事实和已发布知识组织“项目入门、关键规则、常见故障”手册，支持维护和导出 | 两种模式 | P2 / M |
| F5 | **问答反馈与知识缺口清单** | 系统不知道哪些问题反复答不好，也难证明实际收益 | 回答反馈、问题分类、待补知识清单；人工筛选典型问题进入回归样本 | 两种模式 | P1 / M，先做轻量版 |
| F6 | **Word/PDF 正文入库** | 附件能存能下载，正文尚不能直接用于检索问答 | 提取文本 → 预览修正 → 人工确认入库 → 引用定位到原文位置 | 两种模式；纯知识库收益更直接 | P2 / L |

### F1：把一次回答变成团队可以复用的知识

**现状依据**：问答已有回答、证据、历史与当前轮次；知识编辑器已有草稿和引用绑定。当前回答操作中未提供“转知识草稿”。已有“从代码新建知识”和“Markdown 生成草稿”，可复用相关基础。[E1][E2]

- 第一版直接整理选中回答及引用，不依赖再调用模型；可修改标题、正文和知识类型。
- 来源保留会话轮次、知识修订或代码版本。失效引用给出提示，发布时继续执行现有检查。
- 个人会话转为项目共享知识前，展示将共享的内容；仅有阅读权限的用户可复制回答，提交草稿仍遵循维护权限。
- 验收：完成一次“提问 → 草稿 → 发布 → 再检索命中”；能追溯原证据；重复操作不会误建多份。

### F2：让“发现知识过期”进入实际维护流程

**现状依据**：概览已有知识健康提示，知识页已有分支验证筛选、来源漂移证据及人工确认；已有知识负责人字段。缺口是按人组织的待办、精准跳转与连续处理。[E3]

- 第一阶段在知识管理增加快捷视图，概览问题直接打开对应筛选结果，完成处理后进入下一条。
- 第二阶段再增加任务负责人、复查日期、处理记录；知识负责人和本次处理人分别表示，避免混用。
- 代码项目由来源变化触发复核；纯知识库采用人工标记和约定复查日期，不套用代码漂移机制。
- 验收：从一条健康提示定位到具体知识并完成处理；代码版本变化后不能沿用旧复核结论；处理结果可追溯。

### F3：把代码图谱用于具体的改动判断

**现状依据**：已有静态图谱影响查询、受影响文件/测试线索，以及代码旁的关联知识；尚未形成统一的核查单。[E4]

- 第一版以用户选定的文件/符号和当前分支为输入，不以完整 Git 差异解析为前提。
- 输出四组内容：直接关联、静态传播结果、适用知识规则、人工待检查事项。每项附依据及查询范围。
- “业务规则—实现”关联优先复用人工维护的知识和代码绑定；缺失关系明确显示，后续再评估业务主题目录。
- 验收：规则、文件和测试线索均可回到来源；未分析范围有说明；不将静态图谱结果表述为完整运行时影响，也不直接给出“可以安全上线”的结论。

### F4：交付可维护的项目手册

**现状依据**：技术构成分析、知识正文、引用与历史已经存在；缺少按交接场景组织的成品。[E5]

- 先提供“项目入门、业务规则、故障排查、接口说明”模板和人工选材；内容关联原知识修订。
- 代码项目可加入技术构成、入口文件和关键路径；纯知识库侧重流程、术语、制度与常见问题。
- 第一版导出 Markdown/HTML，标记生成时间、资料范围和待补章节；后续再做源知识变更后的更新提示。
- 验收：每条事实能回到源知识或代码；材料不足时保留待补项；选定资料更新后可重新生成。

### F5：用失败问题推动知识补全

**现状依据**：已有问答历史、证据状态、引用覆盖诊断和验证样本；本次检查未发现回答反馈与维护任务的业务闭环。[E1][E6]

- 提供“有帮助 / 未解决”，未解决原因包括未找到资料、资料过期、引用不符、问题理解有偏差。
- 首版由用户主动提交问题及选定证据给维护者，提交前预览；个人会话不默认变成团队可见记录。
- 维护者确认问题类型，补充知识或记录模型/检索问题；问法相似只提示关联，不自动合并结论。
- 验收：反馈 → 处理 → 同题复测可追踪；报表展示样本量和统计范围；引用覆盖率不等同于回答正确率。

### F6：让已有文档真正成为可引用资料

**现状依据**：附件服务提供上传、存储和下载，已有 Markdown 来源处理；Word/PDF 正文提取和位置引用需要新增实现。[E7]

- 先支持 DOCX 和带文本层的 PDF；DOCX 按标题/段落定位，PDF 按页定位，不虚构稳定的 Word 页码。
- 提取结果必须可预览修正，保留原文件和内容版本；更新文件后能够识别受影响片段。
- 扫描件 OCR、复杂表格和图片语义单独评估；首版明确标记未提取内容。
- 验收：用一份真实制度或设计文档完成导入、检索、问答和原文定位；解析失败有具体原因，撤回资料后对应内容不再进入可用证据。

## 三、十项交互改进

“已定位”表示源码可确认当前行为；“流程增强”表示在已有能力上提出更顺畅的交互，效果需试点验证。

| 编号 | 现状与问题 | 建议调整 | 判定 / 优先级 / 投入 |
| --- | --- | --- | --- |
| U1 | MCP 指南称 `branchId/contextId` 可选，并示例只传项目；后端已要求二者之一 | 修正文案和参数示例，补充解析上下文的步骤；纯知识库说明虚拟分支使用方式 | 已定位 / P0 / S |
| U2 | 问答用空模型 ID 同时表示“未选择”和“明确使用本地证据”，后续发送可能重复弹出推荐 | 分开保存“未决定 / 本地证据 / 指定模型”；初次未选择时推荐，明确选择后本会话不再打断；模型失效时重新提示 | 已定位 / P0 / S |
| U3 | 编辑器防误点遮罩，但空闲时取消、关闭或 Esc 可直接关闭；未见未保存变更拦截 | 有改动时提示保存草稿或放弃；覆盖弹窗关闭、页面切换和项目切换；不产生额外已发布修订 | 已定位 / P0 / S–M |
| U4 | 概览“处理知识”统一进入知识页，没有携带对应问题筛选 | 按“待复核、未审核、缺维护人”带条件跳转；显示筛选标签并可一键清除 | 已定位 / P1 / S–M |
| U5 | 总览提交准备任务后提示去项目管理看进度；分支工作区已有轮询 | 在发起处复用任务阶段和失败处理入口，完成后提供“继续检索/继续提问”；保留原问题 | 流程增强 / P1 / M |
| U6 | 代码接入等待任务完成后刷新列表，成功提示强调代码版本已发布；这不等于内容、图谱和向量都就绪。纯知识库创建后已跳转知识页 | 展示“代码已接入 / 检索可用 / 图谱可用”分项状态和下一步；在纯知识库的空状态中引导新建第一条知识 | 流程增强 / P1 / M |
| U7 | 纯知识库已有全部/已发布/草稿范围，但全部内容筛选与已发布相关度检索的行为不同 | 输入框随范围说明“筛选标题/正文/标签”或“检索已发布知识”；零结果时给出切范围、换词或新建知识的可用动作 | 流程增强 / P1 / S |
| U8 | 问答已有证据展开和跨页定位，查原文仍需离开会话 | 增加轻量原文侧栏；深入源码/图谱仍可跳转并保留原轮次。历史引用只展示可取得的原证据，不用当前文件冒充历史版本 | 流程增强 / P1 / M |
| U9 | 知识保存生成草稿并定位到卡片，未找到列表项时打开详情；下一步发布主要从列表发起 | 在已有定位基础上给出“预览 / 继续编辑 / 确认发布”；发布入口只对具备权限者出现，继续保留现有发布确认 | 流程增强 / P1 / S–M |
| U10 | MCP 已有令牌管理、配置复制与排错文字，接入成功需要自行判断 | 增加诊断流程：连接与认证 → 工具发现 → 项目/分支 → 一次只读检索；分清服务端自检和真实客户端接通 | 新交互能力 / P1 / M |

### 展示形式：保留卡片，增加维护视图

知识阅读沿用卡片：标题、摘要、类型、适用状态和少量主要操作。F2 工作台采用紧凑列表，集中比较负责人、待办原因和处理状态，避免每次复核都滚动整屏卡片。

纯知识库保留“知识管理 + 知识问答”主导航，虚拟分支作为后台上下文保留；使用页可将其收进项目详情。代码项目继续突出真实分支和版本，维护操作始终显示目标范围。

引用诊断、模型和索引明细已有折叠基础，继续按需展开。优先解释“现在能做什么、下一步做什么”，不再增加一层泛化的总览页面。

## 四、实施顺序建议

| 批次 | 范围 | 交付判断 |
| --- | --- | --- |
| A：先减少操作阻碍 | U1–U3，随后 U4、U7、U9 | 示例与接口一致；模式选择不重复打断；编辑输入不因误关闭丢失；问题可精准定位 |
| B：形成知识积累与维护流程 | F1、F2 第一阶段、F5 轻量版；配合 U5、U6、U8 | 一次使用可以沉淀知识，一条复核或反馈可以处理完毕，并且能重新验证结果 |
| C：按真实主场景扩展 | 研发团队优先 F3；资料型团队优先 F6；有交接需求再做 F4；U10 在 MCP 推广前完成 | 用真实改动、真实资料或真实交接任务完成验收，再决定扩展范围 |

F2 的首版可以先复用状态和负责人字段组织视图；期限、分派、提醒需要另行设计数据与权限。F5 先记录有效反馈，再考虑聚类和统计看板。无需一次把六项能力全部铺开。

## 五、如何判断优化有效

先采集代码项目和纯知识库各自的基线，再比较同类任务。以下是建议新增或补充采集的指标，当前没有可据此宣称达成的收益数值。

| 指标 | 明确口径 | 对应改进 |
| --- | --- | --- |
| 首次可用完成率 | 新建项目中，在观察期内完成首次有效检索或首次知识发布的项目占比；两种模式分开统计 | U5、U6 |
| 知识沉淀转化 | 从回答创建的草稿中，最终发布的比例；同时观察发布后是否被检索或引用 | F1 |
| 复核处理时长 | 待复核事件产生至人工完成处理的时长；按项目、原因和版本范围统计 | F2 |
| 问题解决情况 | 在主动反馈样本中，标记已解决的占比；同时展示反馈数量和反馈率 | F5 |
| 同题回归结果 | 固定问题、证据范围和模型配置，人工复核来源可追溯性与回答是否支持结论 | F5、F6 |
| 交接与核查用时 | 相同任务、相近经验人员，在可比项目上的完成时长及遗漏项 | F3、F4 |

卡片数、图谱节点数和引用覆盖率可以说明内容或处理规模，不能单独证明业务知识覆盖完整或回答正确。减少操作次数的建议也需要实际流程测量后再给收益比例。

## 六、暂不放进首轮的方向

| 方向 | 原因及后续进入条件 |
| --- | --- |
| 纯知识库原地接入代码 | 按此前约定保留到后续；需专门设计知识、虚拟分支与真实分支身份衔接 |
| 自动发布 AI 生成知识 | 当前价值依赖证据和人工确认，优先提供可审阅草稿 |
| 跨项目统一业务图谱 | 当前主要能力围绕项目/分支；先验证项目内的术语与规则关联，再处理跨项目身份、权限和版本 |
| 自动改代码、提交 PR、自动审批上线 | 明显扩大只读分析与知识管理的范围，需要独立立项与验证 |
| 一次支持所有文档与数据源 | 先验证 DOCX、文本 PDF 的提取和引用质量，再扩展 OCR、Wiki 等来源 |
| 大型经营看板与“AI 可信度总分” | 先建立可解释指标和真实样本，避免用规模统计替代效果 |
